# ADR-011: Contract-First API with OpenAPI

**Status:** Accepted
**Date:** 2026-10-21
**Deciders:** Engineering
**Requirement IDs:** — (governs the API workflow)

---

## Context

Chlat-Park has three consumers of the same domain rules: the Next.js web app, the Telegram module
inside the API, and the local parking service planned for Phase 6. The plan's §15 warns about the
failure explicitly:

> *"Keep domain rules in the backend/domain layer, not duplicated across Next.js and Telegram."*

The failure mode is familiar and it is subtle. The website grows a special case for a status the
API does not return. The bot grows its own interpretation of a fee. The API grows a third. Each
one works. Each one is tested. No two agree. The disagreement surfaces in production, as a ticket
the website would have issued but the bot did not, or a fee the owner cannot explain.

There are two broad ways to prevent it:

| Approach | How | Weakness |
|---|---|---|
| **Code-first** | Write the code, then generate the documentation from it | The documentation describes what the code happens to do. A wrong behaviour is documented faithfully. |
| **Contract-first** | Define the shapes first; generate both the server's validation and the client's types from them | The shapes are a design artefact that must be reviewed, and they can still be wrong — but they are wrong *visibly*, before the implementation. |

The second is the standard answer, and it fits the spec-driven workflow this project has adopted:
the spec says what the behaviour is, the contract says what the shape is, and the code implements
both.

## Decision

1. **The request and response shapes live in `@chlat/contracts`** as **Zod** schemas. They are the
   single source of truth.

2. **The same Zod schema is used twice:**
   * to generate the **OpenAPI 3.1** document at `specs/api/openapi.yaml`;
   * to **validate the incoming request** at the API boundary, via a global validation pipe.

   The two therefore cannot disagree. This is the mechanism that makes the contract-first approach
   real rather than ceremonial.

3. **The OpenAPI document is a build artefact**, generated by
   `pnpm --filter @chlat/contracts openapi`. It is committed to the repository, and it is **never
   hand-edited**.

4. **A CI drift check regenerates the document and fails the build if it differs** from the
   committed one (`pnpm --filter @chlat/contracts openapi --check`). A schema change that was not
   regenerated fails; a hand-edit fails.

5. **The typed client in `@chlat/api-client` is generated from the OpenAPI document**, so the web
   app cannot call a field that does not exist in the contract.

6. **The Telegram module calls the domain services directly**, not the HTTP API. It shares the
   Zod schemas and the services with the web-facing endpoints, so the bot's behaviour is the
   website's behaviour by construction. The contract documents the HTTP surface; it is not the
   mechanism that keeps the bot and the site in agreement.

7. **The permission catalogue and the state enums live in `@chlat/contracts` too**, so the API, the
   web app, the seed script, and the CI route audit all read the same definitions.

8. **The error envelope is part of the contract:**
   ```jsonc
   { "error": { "code", "message", "details?", "requestId" } }
   ```
   The `code` is a stable, locale-independent identifier that clients switch on. The `message` is
   localised and may change.

9. **The contract is versioned in the path** (`/api/v1`). A breaking change bumps the prefix. A
   deprecated endpoint is marked `deprecated: true`, is logged when called, and survives at least
   one pilot cycle.

10. **The contract is reviewed before the implementation.** A pull request that changes a schema
    includes the regenerated document, and the reviewer reads the diff of the *contract*, not only
    the diff of the code.

## Consequences

### Positive

* **The three consumers cannot drift on the shapes.** A shape change breaks the build in every
  consumer at once, rather than producing a runtime mismatch in one of them.
* **The API cannot accept a request the contract does not describe.** The validation is the same
  schema; a `.strict()` schema rejects the unknown fields.
* **The contract is a reviewable design artefact.** The reviewer sees "the response now includes
  `feeAmountMinor`" rather than "the controller returns something new".
* **The client is typed end to end.** A rename in the contract is a compile error in the web app.
* **The OpenAPI document cannot rot.** It is regenerated and diffed in CI.
* **The domain rules stay in one place.** The contract is about *shapes*; the rules are in the
  services. A rule cannot be expressed in a schema.

### Negative

* **The Zod schemas are a second place to write the shapes.** The schema and the service's
  TypeScript types must agree, and the drift check is what keeps them honest.
* **A schema-first workflow is slower to start.** The shapes are designed before the code, which
  feels slow for a small change. It is faster to *finish*, because the mismatch bugs do not exist.
* **The generated client adds a build step.** The `packages/api-client` must be generated before
  the web app compiles.
* **OpenAPI 3.1 support varies by tooling.** The generator and the consumers must agree on the
  3.1 dialect; a 3.0-only consumer may need a conversion.
* **The contract can be wrong.** The contract-first workflow makes the wrongness *visible*; it does
  not prevent it. The acceptance criteria and the tests remain the real guarantee.

## Alternatives considered

| Alternative | Why rejected |
|---|---|
| Code-first with a generated document | The document describes what the code does, including the mistakes. |
| A hand-written OpenAPI document plus hand-written validators | Two artefacts to keep in agreement, with no mechanism to check them. This is the classic source of contract drift. |
| A hand-written document plus Zod validation | Better than the above, but the document and the schemas can still diverge. The generator removes the divergence entirely. |
| GraphQL | A different trade-off: a nicer client, more server complexity, and no built-in HTTP caching. The workload is CRUD plus a few domain operations; REST with a generated contract is the simpler fit. |
| gRPC | Excellent for internal service-to-service calls, poor for a browser client and for the Telegram webhook. The web app needs HTTP. |
| Sharing the domain services directly with the web app | The web app is a separate deployment, so it must go over HTTP. The generated client is the boundary. |
| Protobuf with a JSON gateway | Adds a gateway, a schema language, and a codegen step for a problem the Zod-plus-OpenAPI approach already solves. |
